# Backend guide

This folder contains the Rescue Mesh API and its supporting services. The
comments added to source files explain the main responsibilities; this guide
describes how the pieces fit together and how to run them.

## Start and build

Run these commands from the `backend` directory:

| Command | What it does |
| --- | --- |
| `npm install` | Installs the exact dependency versions recorded in `package-lock.json`. |
| `npm run dev` | Starts the TypeScript server in development mode and restarts it when source files change. |
| `npm run build` | Type-checks and compiles `src/` TypeScript into `dist/`. |
| `npm start` | Starts the compiled server from `dist/index.js`. Run `npm run build` first. |
| `npm test` | Runs the Vitest tests once. |
| `python src/ai_engine.py` | Runs example priority calculations using the Python mirror of the TypeScript rules. |

The HTTP API listens on port `4000` by default; set `PORT` to override it.
The Yjs WebSocket server listens on port `1234` by default; set `YJS_PORT`
to override its port. `YJS_ROOM` changes the room name printed in the startup
log; the Yjs connection handler itself is mounted without a fixed room in
this entry point. `.env` values are loaded at startup by `dotenv`.

## Folder and file map

### `src/`

- `app.ts` creates the Express app, configures JSON and CORS middleware,
  declares the health, SOS, request-list, resource-list, and assignment
  endpoints, and translates validation/domain errors into HTTP responses.
- `index.ts` is the process entry point. It loads environment variables,
  starts the Yjs WebSocket and HTTP/Socket.IO servers, mounts hardware-sync
  routers, and loads/saves the store snapshot.
- `priority.ts` calculates the SOS priority score from the message,
  population, and resource request; it also derives severity labels and a
  human-readable summary.
- `store.ts` holds SOS requests and resource availability in memory. It
  creates and lists requests, assigns resources, resets test state, and
  exposes helpers for snapshot persistence.
- `types.ts` defines the TypeScript contracts shared by the API, store,
  priority engine, and sync handlers, including request, resource, and LoRa
  types/constants.
- `validation.ts` defines Zod schemas for incoming SOS, assignment, ESP32,
  and LoRa request data. The API uses these schemas to reject malformed
  payloads.
- `ai_engine.py` is a Python mirror of the TypeScript priority calculation.
  Keep its keyword weights and severity thresholds aligned with
  `priority.ts`.
- `sync/esp32.ts` defines `POST /sync_esp32`; it fetches requests from an
  ESP32 device, skips already-known requests, imports new requests into the
  store, and emits a Socket.IO event for each imported SOS.
- `sync/lora.ts` defines `POST /sync_lora` to import requests from a LoRa
  gateway and `GET /simulate_lora` to return sample packets for testing
  without gateway hardware.

### `test/`

- `priority.test.ts` tests priority scoring, severity thresholds, explicit
  score handling, and score clamping.

### `data/`

- `snapshot.json` is runtime persistence data, not source code. On startup,
  the server restores its `requests` and `resources`; while running it saves
  a fresh snapshot every 30 seconds and during normal termination.
- `.gitkeep` keeps this directory present when it has no other tracked files.

### Backend configuration and generated files

- `package.json` declares the backend package metadata, npm scripts, and
  runtime/development dependencies.
- `package-lock.json` records the resolved dependency tree for repeatable
  installs. It is generated by npm and should not be manually annotated.
- `tsconfig.json` configures TypeScript compilation, strict checking, and
  output to `dist/`.
- `dist/` contains compiled output produced by `npm run build`; edit `src/`
  rather than generated files.
- `node_modules/` contains installed packages managed by npm; it is not
  application source and should not be edited for backend explanations.

## Main API flow

1. `POST /send_sos` validates the request, calculates missing priority
   metadata, stores the new SOS, and broadcasts `sos_created`.
2. `GET /get_requests` returns stored SOS requests, optionally filtered by
   the `status` query parameter and ordered by priority.
3. `GET /resources` returns the available resource records and their current
   availability.
4. `POST /assign_resource` assigns explicitly selected resource IDs or picks
   a preferred available resource, updates availability, and broadcasts
   `resource_assigned`.
5. `POST /sync_esp32` and `POST /sync_lora` import requests from their
   respective gateways. `GET /simulate_lora` provides sample LoRa packets;
   it does not itself import them.
6. `GET /health` reports that the backend process is responding.

The request and resource store is in memory while the process runs.
`data/snapshot.json` is used to restore it after a restart; it is not a
database or a live Yjs-backed store.
